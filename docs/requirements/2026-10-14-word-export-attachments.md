# Word Export — Embedded Attachments（导出时嵌入附件内容）

> 特性名 `word-export-attachments`，从用户描述「导出页面为 word，但 word 中只有附件名称，没有附件」归一化而来。

## Problem（用户反馈）
页面可导出为 Word，但生成的 .docx 里**只显示附件名称**，没有附件的实际内容（图片本体 / 文件本体）。用户期望页面中的附件随导出一并嵌入文档，使导出的 docx 能独立还原页面信息。

## Behaviors
- 解析页面内容中的附件节点（图片、文件等），识别其存储引用（URL / 文件 key / 资产 ID）。
- 读取附件实际内容（图片字节或文件流），将其嵌入生成的 .docx，替代单纯的名称占位（如 `docx` 的 `Image` 段落或嵌入对象）。
- 导出后的 docx 在**不依赖在线服务**的情况下，能离线展示附件内容。
- 对无法读取 / 超大 / 不支持的附件做降级处理（保留名称 + 标注），不阻塞整体导出。

## Acceptance Criteria
- 含图片附件的页面导出后，docx 内能看到图片本体（非仅文件名）→ 手动 / 集成（打开 docx 校验 image part 存在）。
- 含文件类附件的页面导出后，docx 内能打开 / 看到文件内容或嵌入对象 → 手动。
- 附件缺失 / 读取失败时，导出不报错中断，docx 保留名称并标注 → 集成 / 单测。
- 导出侧逻辑有单测覆盖附件读取与嵌入（mock 存储读取）→ test。

## Context
- 技术栈：NestJS 后端 + `docx` 库（ESM-only）生成 .docx；前端 React / Mantine。
- 相关功能：`word-export-error`（已完成，docx 导出主链路 + 前端拦截器，本功能在其导出主链路上增强）；`recycle-bin`（无关）。
- 附件存储：需在 plan 阶段调查附件在系统中的存储方式（本地磁盘 / S3 / DB blob）及读取 API，以及如何从页面内容节点映射到附件资源。
- 约束：参考 `word-export-error` 的 ESM/Jest 限制（`docx` 等依赖为 ESM-only，单测需 mock，真实 .docx 字节生成需运行时/e2e 验证）。

## Constraints
- 优先不改后端导出接口契约；如需新增读取附件内容的内部服务方法，应局部、可逆。
- 不引入对在线服务的硬依赖（导出结果应可离线查看）。
- 附件体积较大时需注意内存 / 流处理，避免大文件拖垮导出。

## Non-goals
- 不处理非页面附件的全局导出。
- 不重写 docx 导出的整体管线（仅增强附件处理分支）。
- 不改动软删除 / 回收站等无关逻辑。
